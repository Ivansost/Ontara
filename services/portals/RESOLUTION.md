# Controlled Roads demo completion

This is a synthetic authority action on an accepted Roads demo ticket. It does
not contact a municipality or verify a physical repair. It adds one immutable
`resolution` object to that ticket. Accepted receipts, submitted versions and
facts, ticket version, access token, form snapshots and request counters remain
unchanged. The existing ticket page then says **Resolved in demo** and explains
that physical repair has not been verified.

## Read stored receiving status

```text
GET /v1/portals/roads/tickets/{ticketId}/status?runId=...&accessToken=...
```

Use the saved ticket capability from the accepted receipt's `ticketUrl` or
`updateUrl`. The API must build this path from its configured receiving origin
and bound ticket ID, rather than accept a caller-supplied URL. Run, ticket and
capability must match; a presenter bearer token does not replace the capability.
Keep the query parameters private and out of logs and public evidence.

An accepted, unresolved ticket returns:

```json
{
  "runId": "demo-run-001",
  "portalId": "roads",
  "ticketId": "RDS-EXAMPLE",
  "ticketVersion": 1,
  "status": "acknowledged",
  "isDemo": true,
  "simulated": true,
  "physicalRepairVerified": false,
  "resolution": null,
  "updateAllowed": true
}
```

After completion, `status` is `resolved`, `updateAllowed` is `false`, and
`resolution` contains the stored record below. Its `ticketVersion` equals the
top-level version. This GET does not record a lookup request or change counters.
Incorrect run/capability/ticket returns 404; a ticket without matching receiving
acceptance returns 409. Graffiti is outside this bounded feature and returns 422.

## Mark one simulated completion

```text
POST /internal/v1/runs/{runId}/portals/roads/tickets/{ticketId}/resolution
Authorization: Bearer <existing DEMO_PORTAL_ADMIN_TOKEN>
Content-Type: application/json
```

```json
{
  "resolutionId": "resolution-stable-001",
  "expectedTicketVersion": 1,
  "status": "resolved",
  "isDemo": true,
  "simulated": true,
  "physicalRepairVerified": false
}
```

Only `resolutionId` and `expectedTicketVersion` are required. The other four
fields default to the displayed values and reject contradictions. IDs use the
existing stable-ID grammar: 4–128 characters, starting with an ASCII letter or
digit, followed by letters, digits, `.`, `_`, `:`, or `-`. The version must be a
strict positive integer. Unknown fields, caller-supplied timestamps/messages,
coerced booleans and alternative status values return 422. Invalid presenter
authentication returns 401. This secret stays in the private presenter CLI;
it is not transferred to the API, executor or resident browser.

HTTP 200 returns the exact stored record on both first acceptance and replay:

```json
{
  "schemaVersion": 1,
  "resolutionId": "resolution-stable-001",
  "runId": "demo-run-001",
  "portalId": "roads",
  "ticketId": "RDS-EXAMPLE",
  "resolvedAt": "2026-11-14T20:00:00Z",
  "status": "resolved",
  "isDemo": true,
  "simulated": true,
  "physicalRepairVerified": false,
  "ticketVersion": 1,
  "message": "The simulated demo authority marked this report resolved. Physical repair has not been verified."
}
```

`resolvedAt` is generated by the receiver. One partial unique index reserves a
resolution ID for one ticket. Replaying the same ID and expected ticket version
returns the original timestamp and record. Changing either returns 409. A missing
run or scoped ticket returns 404; no matching accepted create receipt, a stale
ticket version, or reuse of another ticket's resolution ID returns 409. Nothing
creates or resets a run through this endpoint.

## Terminal update and concurrency rules

The resolution write is a single conditional MongoDB update requiring the
expected ticket version, matching accepted receipt and absence of a resolution.
It only sets `resolution`. Ticket updates also require the current version and
absence of a resolution. If an update wins first, the stale resolution returns
409. If the resolution wins first, the new update returns 409 without acceptance.

After resolution, both JSON/browser POSTs reject new updates and the update form
GET returns 409. Exact replay of an already accepted update still returns its
original receipt, including when its old form version has since changed. The
capability, reference, approved digest and submitted form digest must all match.
Rejected or replayed update requests retain the existing attempt-counter
semantics; no additional accepted update is counted. Historical receipt HTML is
unchanged and remains evidence of acceptance rather than repair.

## Local qualification

`tests/test_resolution.py` covers presenter/capability/run scope, strict input,
unaccepted tickets, immutable replay, resolution-ID uniqueness, unchanged records
and counters, accepted old-form replay, and both conditional-write race orders.
The complete local suite passes with mongomock. This is local code qualification;
deployment and actual Atlas/API/mail reconciliation are separate integration
checks owned by the coordinator. No provider or runtime call is needed by this
receiving feature.
